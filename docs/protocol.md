# ShoutWars 通信仕様

ShoutWars のクライアントとサーバーの間の通信仕様を定める。

**実装ではなく本仕様が正である。** 食い違う場合は実装を修正する。

対象 API バージョンは **`/v3`**。`/v2` からの変更点は §4.1 にまとめる。

起草には Claude Code を使用した。


## 1. 概要

### 1.1 責務

サーバーの責務は次の 3 つに限られる。

1. **部屋の管理** — 作成、参加、寿命、メンバーシップ
2. **同期** — 全ユーザーのイベントを集約し、全員に同一の集合を同一順序で配る
3. **可用性の防衛** — サイズ・件数の上限、期限切れの回収

### 1.2 非責務

サーバーが明示的に行わないこと。

#### ゲームの状態を持たない・解釈しない

サーバーはゲームロジックを一切実行しない。ゲームの状態はすべてクライアントが持つ。

#### チート対策を行わない

ゲームの仕様上、クライアント側でのチートは容易である (音声認識をキー入力に差し替えるだけで有利になる)。したがってサーバー側で部分的に対策しても意味がないため、行わない。

> **可用性はこれとは別である。** 「チート対策をしない」は「何も検証しない」を意味しない。サイズ・件数の上限 (§6) はチート対策ではなく、メモリ枯渇によるサービス停止への対策であり、責務に含まれる。

#### 特定の型の中身を解釈しない

次の値はサーバーにとって不透明であり、汎用の値型のまま保持して素通しする。

| 値 | 位置 |
|---|---|
| `room_info` の中身 | 部屋ごとに 1 つ |
| 各イベントの `data` の中身 | イベントごと |

サーバーはこれらを読まず、書き換えず、検証しない (サイズの上限を除く)。

### 1.3 用語

| 用語 | 定義 |
|---|---|
| **部屋 (room)** | 同期の単位。ロビーとゲームの 2 状態を持つ |
| **ユーザー (user)** | 部屋への 1 回の参加。UUIDv7。同一人物との対応は保証しない |
| **セッション (session)** | 認証の単位。部屋の作成・参加時に発行される |
| **tick** | 同期の単位時間。100 ms |
| **同期レコード (sync record)** | 1 tick 分のイベント集合 |
| **tick 番号** | 部屋の作成時を 0 とする連番。レコードの識別子であり順序 |
| **報告イベント (report)** | 状態の複製。送信者には返らない |
| **確認イベント (action)** | コマンドの確定。送信者にも返る |
| **部屋主 (owner)** | 部屋にいるユーザーのうち、ID が最も若い者 |

## 2. 同期モデル

### 2.1 概観

ゲーム中の通信は **tick** という単位で進む。1 tick = **100 ms**。

サーバーは各 tick について **同期レコード** を 1 つ持ち、全ユーザーのイベントを集約して、全員に同一の集合を同一順序で配る。サーバーはイベントの中身を解釈しない。

レコードには **部屋の作成時を 0 とする連番 (tick 番号)** が付く。これがレコードの識別子であり、順序であり、経過時間の基準でもある。ゲーム内の残り時間などは、この値を数えて全員で一致させる。クライアントのローカル時計は使えない (§4)。

イベントには 2 種類あり、**別の仕組み** である。

| | 報告イベント (`reports`) | 確認イベント (`actions`) |
|---|---|---|
| 正体 | **状態の複製** | **コマンドの確定** |
| 例 | 座標と速度 | アイテムの取得 |
| 送信者への返却 | されない | **される** |
| 送信者のローカル適用 | **即時** (待たない) | **確定を待つ** |
| 遅延したとき | **破棄** | **1 tick まで持ち越し** |
| 順序保証 | 不要 | **必須** |

この設計は決定論的ロックステップを基礎にしつつ、状態の複製を併用したハイブリッドである。純粋なロックステップと異なり、クライアントは完全に決定論的なシミュレーションである必要がない。その代わりに衝突解決の規則 (§4) を全員が同じように適用することで一致を保つ。

**全員のデータが揃うまで待って配る** という点は、この設計の中核であり、変更しない。これによってサーバーはゲームを理解しないまま同期を成立させられる。待つことのコストは待ち方の問題であって、待つという意味論の問題ではない。

本仕様は **トランスポートに依存しない。** 「1 tick につき 1 往復」が保たれるならば、HTTP 以外へ移しても意味論は変わらない。

### 2.2 報告イベント — 状態の複製

**用途:** 「今こうなっている」を伝えるもの。座標と速度が典型。

- 送信者は **自分の分を即座にローカル適用する。** 応答を待たない
- 受信側は速度を使って **外挿 (dead reckoning) する。** 速度が無いと他プレイヤーの動きが不連続になる
- 値は絶対値であり、上書きされれば直る。**個々の到達は保証しない**
- **遅れて届いた report は破棄する。** 古い座標を今さら適用すると巻き戻って見える

#### 合流はクライアントの責務

移動の報告は毎フレーム発生し得るため、1 tick (100 ms) の間に同じ内容の報告が何件も溜まる。値が絶対値である以上、**最後の 1 件以外は無意味** である。

**この間引き (合流) はクライアントが送信前に行う。** サーバーは受け取ったものをそのまま中継する。

サーバー側で合流させると、「同じ `type` の報告は上書きされる」というゲームの意味をサーバーが理解することになり、§1.2 に反する。また、合流してよい `type` かどうかを指定する仕組みが別途必要になる。クライアントは自分が何を送っているかを知っているため、そちらで判断する方が正しく、かつ単純である。

遅延した report は破棄されるため、サーバー側で合流すべき場面は存在しない。

### 2.3 確認イベント — コマンドの確定

**用途:** 複数人が同時に行うと衝突するもの。アイテムの取得が典型。

- 送信者は **ローカル適用しない。** サーバーが確定させた tick で、送信者を含む全員が同時に適用する
- そのため `actions` は **送信者にも返る**
- 衝突は **クライアント側で全員が同じ規則を適用して** 解決する。受信順に処理し、先に成立した方を採用する
- 遅れて届いた action は **次の tick に持ち越す。** 持ち越しは 1 tick まで

### 2.4 順序の規則

サーバーが定める順序は次のとおり。**クライアントは受信順に処理するだけ** であり、自分で並べ替えてはならない。

```
順序 = (tick, その tick での送信者の順位, 送信者内の送信順)

送信者の順位 = hash(tick ++ user_id) の昇順
```

| 保証 | 根拠 |
|---|---|
| 全員が同じ順序を受け取る | tick 番号はサーバー採番、ユーザー一覧は全員一致 |
| **同一送信者内の順序は崩れない** | 送信者ごとの配列をそのまま連結する |
| プレイヤー間に恒久的な偏りがない | 順位が tick ごとに入れ替わる |
| **時計に依存しない** | タイムスタンプを順序に使わない |

#### イベント ID は順序を決めない

**イベント ID は識別子であり、順序には使わない。**

イベント ID をクライアントが生成する UUIDv7 とし、その大小で衝突を裁定してはならない。時刻部の物差しがクライアントのローカル時計になるためである。ローカル時計は数百 ms 単位でずれ得るので、ずれが tick 幅を超えると **衝突は毎回同じプレイヤーに倒れ**、当事者は原因に気づけない。

同一 tick 内は定義上「同時」であり、時刻の前後を争うこと自体に意味がない。tick をまたぐ順序は tick 番号が担保する。

> **将来の選択肢:** 1 tick に多数の action が集まる設計になった場合、「送信者ごとに連結する」代わりに「1 件ずつラウンドロビンで差し込む」方式に変更できる。この規則はサーバー内部で完結するため、プロトコルもクライアントも変更を要しない。
>
> 現状は、単語検出に約 0.5 秒を要するため 1 プレイヤーが 1 tick に発火させる action は事実上 1 件以下であり、連結で足りる。

### 2.5 tick の進行

#### パイプライン化

クライアントは **100 ms 周期でリクエストを送信する。前回の応答を待たない。**

```
周期 = max(100 ms, ネットワーク往復)
```

- in-flight は常に 1 本まで。周期が来ても前回の応答が未着なら、到着まで待つ
- イベントの蓄積は継続し、送信時に送信キューをまとめて送る
- 応答は次の窓の途中で到着する。**受信した時点で適用する** (余分に寝かせない)

**応答を待ってから次の窓を開始してはならない。** 蓄積窓とネットワーク往復が直列に並び、周期にラグが丸ごと加算される。重ねることで周期がラグに依存しなくなり、回線の悪いプレイヤーほど効果が大きい。

| RTT | 直列にした場合 | 本仕様 |
|---|---|---|
| 40 ms | 約 165 ms | **100 ms** |
| 100 ms | 約 225 ms | **125 ms** |

> 音声の単語検出に約 0.5 秒を要するため、入力遅延の予算に占めるネットワークの割合はもともと小さい。tick を 100 ms より短くする実益は乏しく、サーバー負荷に見合わない。

tick `N` のレコードが集める窓は `[作成 + N × tick_ms, 作成 + (N+1) × tick_ms)` である。

**tick 幅はサーバーが決め、参加時の応答で `tick_ms` として通知する。** クライアントはこの値に従い、自分で埋め込んではならない。クライアントのバージョンは完全一致を要求する (§3.5) ため、値を変えるたびに再配布が必要になることを避ける。

#### 締め切り

サーバーは **絶対時刻** で各 tick の期限を持ち、**「全員到着」または「期限到来」の早い方** でレコードを締め切る。全員が速ければ従来どおり早く進む。

**締め切りと同時に次のレコードを開く。** 「締め切り済みだが次が開いていない」隙間が生じてはならない。隙間があると、3 人以上の部屋で正常なクライアントが書き込み先を失う。

### 2.6 配送 — カーソルはクライアントが持つ

**クライアントがリクエストに `last_tick` (次に受け取りたいレコードの tick 番号) を含める。** サーバーは `last_tick` 以降を返す。

半開区間 `[last_tick, ∞)` として扱う。「まだ 1 件も受け取っていない」を表す番外の値が要らず、部屋を作った直後は `0` から始まる。

**サーバーが「渡した」と推定してはならない。** レスポンスを書き出す前にカーソルを進めると、レスポンスが届かなかった場合にそのレコードが永久に失われ、しかも検出されない。クライアント側の HTTP タイムアウトで容易に発生する。

| 性質 | |
|---|---|
| **冪等** | 同じ `last_tick` で何度投げても同じものが返る |
| **自己修復** | 取り損ねても次の同期で自動的に再送される |
| **推定が無い** | サーバーは「届いたはず」と仮定しない |

`last_tick` を進めるのはクライアントが **受信して適用し終えたとき** であり、適用し終えたレコードの **次** の番号にする。

#### 保持期間

サーバーはレコードを **10 秒 (100 tick) 分** 保持する。それより古い `last_tick` を申告された場合は追いつけないため、専用のエラーを返し、クライアントは再参加して `room_info` から状態を作り直す (§2.7)。

### 2.7 遅延・不在・脱落・復帰

**不在**と**脱落**を分ける。

| | 判定 | 扱い |
|---|---|---|
| **不在** | 1 tick 応答がない | **即座にバリアの待機対象から外す。** 復帰したら戻す |
| **脱落** | 10 秒応答がない | 部屋から除去する |

脱落まで待機対象に残すと、**4 人中 1 人が落ちただけで残り 3 人が 10 秒間もたつく。**

#### 復帰

復帰に専用の手順は無い。**同じセッションで、保持していた `last_tick` を申告して `/room/sync` を再開するだけ** でよい。取りこぼしたレコードがまとめて返る。

10 秒を超えて不通だった場合は脱落しているため、再参加が必要になる。

#### 不在中のクライアントの契約

- `actions` 由来の状態を **自力で進めてはならない。** 復帰後、未受信のレコードを順に適用する
- `reports` 由来の外挿は続けてよい

### 2.8 メンバーシップ

**ユーザー一覧は、レコードの締め切り時点で固定したスナップショットとして `sync` の応答で返す** (`room_users`)。返すのは、今回返した最後のレコードの締め切り時点のものである。

- 一覧は **ユーザー ID の昇順** に並ぶ。ユーザー ID は UUIDv7 で参加順に増えるため、先頭が常に部屋主になる (§3.4)
- 各ユーザーは不在かどうか (§2.7) を持つ
- ゲームが開始しているかどうかも同じ応答で伝える

**応答の生成時点の一覧を返してはならない。** 同一レコードに対する各人の応答は異なる時刻に生成されるため、その時点の一覧を返すと人によって内容が食い違い、desync する。レコードに固定すれば、同じレコードを受け取った全員が必ず同じ一覧を受け取る。

**差分はクライアントが取る。** 「誰が抜けたか」を知りたい場合は前回の一覧と比べる。一覧は絶対値であり、取りこぼしても次の応答で上書きされて直る。差分の列から状態を組み立てる方式では、一度でも適用を誤ると黙って食い違ったまま進む (§2.2 と同じ理由である)。

**サーバーはイベントを生成しない。** `reports` と `actions` に流れるものはすべてクライアント由来であり、サーバー発のものが混ざることはない。

### 2.9 `room_info`

**遅延参加者用の初期状態スナップショットであり、権威ではない。**

- **参加時の応答でのみ返す。毎 tick 返さない**
- 平常時の変更は通常のイベント経由で行い、各クライアントが自分の `room_info` を更新する
- 部屋主のみが更新でき、他者から送られたものは無視される

### 2.10 desync 検出

**desync** とは、同じイベント列を受け取っているはずのプレイヤー間で状態が食い違うこと。アイテムを取れた人と取れていない人が同時に存在する、といった形で現れる。

**エラーも例外も出ない。** ゲームは何事もなく進行し続け、プレイヤーには「判定がおかしい」としか見えず、サーバーのログにも何も残らない。したがって、検出する仕組みを持たなければ原因の特定は事実上不可能になる。

配送のカーソル (§6) は取りこぼしを **予防** するが、クライアント側の適用ミス、`room_info` からの復元漏れ、報告イベントの合流の食い違いは防げない。**予防と検出は別の仕組みであり、両方を備える。**

#### 適用イベント数の照合 (必須)

クライアントは、これまでに適用したイベントの累計を `applied` として送る。サーバーは自分が配った数を知っているため、比較するだけでよい。

- **取りこぼしと二重適用を検出できる**
- ゲームの内容に一切依存せず、数を比べるだけで済む

#### 状態ハッシュは行わない

ゲームの状態そのものをハッシュして突き合わせる方式は **採用しない。**

対象に何を含めるかを全クライアントで揃え続ける必要があり、揃っていないと誤検出する。ゲームを作りながら常にこれを気にする負担に対して、`applied` の照合を超えて得られるものが現時点で見合わない。

必要になった場合は `applied` と同じ位置にフィールドを追加すればよく、そのときも既存のクライアントを壊さない。

> 増分ハッシュ (Zobrist 法など) は、仮に導入する場合でも適さない。状態が小さく更新頻度も低いため計算量の利点が無く、すべての変更箇所に更新処理を仕込む負担が増える。XOR による増分ハッシュは自己逆元であるため、**二重適用が打ち消し合って一致してしまい**、検出したい故障と噛み合わない。

#### 検出時の扱い

サーバーは不一致を検出したら、レスポンスの `desync` を `true` にして全員に通知する。クライアントは通信エラーとして扱い、ゲームを終了してよい。**食い違ったまま続行するより望ましい。**

### 2.11 サーバーが保証すること

1. 全ユーザーが **同一のイベント集合** を **同一順序** で受け取る
2. 同一のレコードを受け取った全員が、**同一のユーザー一覧** を受け取る
3. 同一送信者のイベントの相対順序は保存される
4. `sync` は **必ず 1 件以上のレコードを返す**
5. tick の境界と、イベントがどの tick に属するかは、**サーバーだけが決める**
6. 締め切られたレコードは **二度と変わらない**

### 2.12 サーバーが保証しないこと

- ゲーム状態の正しさ (解釈しないため)
- チートの防止 (§1 を参照)
- 個々の `report` の到達
- 同一人物が複数ユーザーとして参加しないこと (匿名参加のため識別手段がない)

## 3. 部屋のライフサイクル

### 3.1 状態

部屋は **ロビー** と **ゲーム** の 2 状態を持つ。

```
作成 ──▶ ロビー ──[部屋主が開始]──▶ ゲーム ──[期限切れ]──▶ 削除
           │                          │
           └──────[期限切れ]──────────┴──▶ 削除
```

| 状態 | 期限 | 参加 |
|---|---|---|
| ロビー | 作成から **10 分** | 可 |
| ゲーム | 開始から **20 分** | 不可 |

期限切れの部屋は削除される。**期限切れの部屋には参加できない。** 削除処理が周期実行である場合も、参加時に期限を確認すること。

### 3.2 部屋番号

部屋 ID (UUID) は口頭で伝えられないため、別に **6 桁の数字** の部屋番号を持つ。参加は部屋番号で行う。

- **部屋番号は乱数で採番する。** 使用中の番号が出た場合は引き直す
- 引き直しの回数には上限を設け、超えた場合は `503 room_limit_reached` を返す。上限が無いと、番号が埋まってきたときに際限なく回る
- **削除された番号の再利用に猶予は設けない**

6 桁 = 100 万通りに対して同時に存在する部屋は `ROOM_LIMIT` (既定 100) 程度であるため、直前に消えた番号が再び振られる確率は無視できる。順番に採番する方式であれば猶予が必要になるが、乱数であれば不要である。

乱数採番には、**番号を総当たりして他人の部屋に入ることを困難にする** 副次的な利点もある。

### 3.3 ユーザー

- ユーザーは **部屋への 1 回の参加** を表す。同一人物との対応は保証しない
- ユーザー ID は部屋の中で一意である
- ユーザー名は 32 文字以内
- **同一人物の重複参加は防がない。** 匿名参加であり識別手段がないため
- 人数の上限は部屋の作成時に 2〜4 で指定する

### 3.4 部屋主

- 部屋主は、部屋にいるユーザーのうち **ID が最も若い者**
- 部屋を作成した者が最初の部屋主となる
- **部屋主が抜けた場合、最初に参加した者が引き継ぐ**
- 交代は一覧の並び順に現れる。一覧は ID 昇順であり、部屋主が抜ければ次の者が先頭になる (§2.8)

部屋主だけができること。

- ゲームの開始
- `room_info` の更新

### 3.5 クライアントのバージョン

`create` と `join` は `version` を受け取り、**完全一致のみを許可する。** 一致しない場合は `409 version_mismatch` を返す。

バージョンが異なるクライアントは、イベントの解釈やゲームロジックが食い違い、desync (§2.10) を起こす。サーバーはイベントの中身を解釈しないため、どの差異が安全かを判断できない。したがって互換の範囲を設けず、完全一致を要求する。

クライアントはゲームを更新するたびに `version` を変更する。

### 3.6 セッション

- 部屋の作成・参加時に発行する
- **暗号論的乱数で生成する。** UUIDv7 を使ってはならない
- 脱落 (10 秒無応答) で無効になる
- セッションが無効になったクライアントは、同期を停止しなければならない

セッション ID は bearer トークンであり、これを持つ者はそのユーザーとして振る舞える。UUIDv7 が適さない理由は 2 つある。先頭 48 bit がタイムスタンプであり秘密にならないこと、そして残る 74 bit の扱いが RFC 9562 で実装依存とされており、**乱数とは限らない** ことである。本仕様は UUIDv7 の単調性に依存する箇所を持たないが (§2.4)、単調性と予測困難性はそもそも相反する。順序を必要としない値に、順序のための生成器を使う理由がない。

### 3.7 ゲームの開始

部屋主が開始すると、**新たな参加ができなくなる。** それ以外の意味を持たない。ゲームの進行そのものはクライアントが管理する。

開始した事実は `sync` の応答の `started` で全員に伝わる (§2.8)。部屋主だけが知る状態にしてはならない。

### 3.8 ゲームの終了

**サーバーは「ゲームが終わった」という概念を持たない。** 決着はクライアントが判定し、部屋は期限切れとともに削除される。

**同じ部屋での再戦は行わない。** もう一度対戦する場合は部屋を作り直す。サーバーに状態遷移を増やさず、単純さを保つことを優先した判断である。

## 4. API

エンドポイントは `/v3`。Request と Response の body は MessagePack で表す。Content-Type は `application/msgpack`。

環境変数 `PASSWORD` が設定されている場合、リクエストヘッダの `Authorization` に `Bearer ${PASSWORD}` を指定する。

`uuid` は UUID の文字列表現とする。**プリミティブでない型 (`RoomInfo`、`Event` の `data`) はサーバーが解釈しない** (§1)。

以降のスキーマは構造を示す記法であり、そのままの文字列が流れるわけではない。値の位置に書かれた `string` や `uuid` は型を表す。

### 4.1 `/v2` からの変更点

| 変更 | 理由 |
|---|---|
| **`sync_id` (UUID) を廃止し `tick` (整数) に置換** | 順序と経過時間の基準を兼ねる (§2.1) |
| `sync` のリクエストに **`last_tick`** を追加 | 配送のカーソルをクライアントが持つ (§2.6) |
| `sync` のリクエストに **`applied`** を追加 | desync 検出 (§2.10) |
| `sync` のリクエストから **`room_info` を削除** | 参加時のみに変更 (§2.9) |
| `sync` のレスポンスの **`room_users` をレコード単位に固定** | 応答の生成時刻で内容が変わらないようにする (§2.8) |
| イベント ID を **順序に使わない** | ローカル時計への依存を排除 (§2.4) |
| **`429` の規則を廃止** | パイプライン化 (§2.5) |
| エラー body に **`code` を追加** | §5 |
| `join` で **期限を確認** | §3.1 |
| `create` / `join` の応答に **`tick_ms`** を追加 | tick 幅をサーバー側のつまみにする (§2.5) |
| イベントの `event` を **`data` に改名** | 中身を解釈しない値であることを名前に合わせる |

### 4.2 `POST /v3/room/create`

部屋を作成する。

#### Request

```jsonc
{
  "version": string,   // クライアントのバージョン
  "user": { "name": string },  // ユーザー名 (32 文字以内)
  "size": number       // 部屋の人数 (2〜4 の整数)
}
```

#### Response

```jsonc
{
  "session_id": uuid,  // セッション ID
  "user_id": uuid,     // 自分のユーザー ID
  "id": uuid,          // 部屋 ID
  "name": string,      // 部屋番号 (6 桁の数字)
  "tick": number,      // 最初の同期で申告する last_tick
  "tick_ms": number    // tick の幅 (ミリ秒)
}
```

### 4.3 `POST /v3/room/join`

部屋に参加する。ロビー状態の部屋にのみ参加できる。

#### Request

```jsonc
{
  "version": string,
  "name": string,      // 部屋番号 (6 桁の数字)
  "user": { "name": string }
}
```

#### Response

```jsonc
{
  "session_id": uuid,
  "user_id": uuid,
  "id": uuid,
  "room_info": RoomInfo, // 現在の部屋情報 (これで初期化する)
  "tick": number,        // 最初の同期で申告する last_tick
  "tick_ms": number      // tick の幅 (ミリ秒)
}
```

### 4.4 `POST /v3/room/sync`

同期する。クライアントは `tick_ms` 周期で送信し、前回の応答を待たない (§2.5)。in-flight は 1 本まで。

#### Request

```jsonc
{
  "session_id": uuid,
  "last_tick": number,   // 次に受け取りたいレコードの tick 番号
  "applied": number,     // これまでに適用したイベントの累計 (desync 検出用)
  "reports": [{ "id": uuid, "type": string, "data": Data }],
  "actions": [{ "id": uuid, "type": string, "data": Data }]
}
```

`room_info` は送らない。更新はイベントとして送る。

#### Response

```jsonc
{
  "tick": number,   // 次回申告する last_tick (今回返した最後のレコードの次)
  "room_users": [{  // ID 昇順。先頭が部屋主
    "id": uuid,
    "name": string,
    "absent": bool  // 直前の tick に応答が無かった (§2.7)
  }],
  "started": bool,  // ゲームが開始しているか (§3.7)
  "reports": [{
    "id": uuid,
    "tick": number, // このイベントが属するレコード (最後のレコード以外に属する場合のみ)
    "from": uuid,
    "type": string,
    "data": Data
  }],
  "actions": [ /* 同上。送信者自身のものも含む */ ],
  "desync": bool    // 不一致を検出した場合に true
}
```

- `reports` と `actions` は **サーバーが定めた順序** で並ぶ (§2.4)。クライアントは並べ替えず、先頭から順に処理する
- 複数レコード分がまとめて返ることがある
- **必ず 1 件以上のレコードを含む**
- `room_users` と `started` は、今回返した **最後のレコードの締め切り時点** の値である (§2.8)

### 4.5 `POST /v3/room/start`

ゲームを開始する。部屋主のみが送信できる。新たな参加ができなくなる (§3.6)。

#### Request

```jsonc
{ "session_id": uuid }
```

#### Response

```jsonc
{}
```

開始した事実は、全員の `sync` の応答の `started` に現れる。

### 4.6 `GET /v3/status`

#### Response

```jsonc
{
  "room_count": number,
  "room_limit": number
}
```

## 5. エラー

### 5.1 形式

エラーは対応する 4xx / 5xx のステータスコードと、次の body で返す。

```jsonc
{
  "error": {
    "code": string,   // 機械可読な識別子
    "message": string // 人間向けの説明。UI に表示してよい
  }
}
```

`code` で分岐し、`message` は表示にのみ使う。これにより表示文言を変更してもクライアントの分岐が壊れない。

### 5.2 コード一覧

| ステータス | `code` | 意味 |
|---|---|---|
| 400 | `bad_request` | リクエストの形式が不正 |
| 400 | `limit_exceeded` | 上限を超えた (§6) |
| 413 | `limit_exceeded` | リクエストの本文が上限を超えた (§6) |
| 401 | `unauthorized` | パスワードが不正 |
| 401 | `invalid_session` | セッションが無効または期限切れ |
| 403 | `not_owner` | 部屋主のみが可能な操作 |
| 403 | `already_synced` | 同一 tick に二重に同期しようとした |
| 404 | `room_not_found` | 部屋が存在しない、または期限切れ |
| 409 | `version_mismatch` | クライアントのバージョンが合わない |
| 409 | `room_full` | 部屋が満員 |
| 409 | `game_started` | 既にゲームが開始している |
| 410 | `sync_too_old` | 申告された `last_tick` が保持期間外 |
| 503 | `room_limit_reached` | サーバーの部屋数が上限に達している |
| 500 | `internal` | サーバー内部の誤り |

### 5.3 存在の秘匿について

**セッションの検証を先に行う。** セッションが無効なら `401 invalid_session` を返し、部屋の存在には言及しない。セッションが有効な場合にのみ、部屋の状態に応じた `404` や `409` を返す。

### 5.4 復帰の指針

| `code` | クライアントの対応 |
|---|---|
| `sync_too_old` | 同期を停止し、再参加して `room_info` から作り直す |
| `invalid_session` | 同期を停止する。脱落している |
| `room_not_found` | 同期を停止する。部屋は消えている |
| `limit_exceeded` | 送信量を減らす。正常なクライアントは到達しない |
| `internal` | 再試行してよい。継続するようならサーバーの不具合 |

## 6. 制限値

これらは **チート対策ではなく、メモリ枯渇によるサービス停止を防ぐためのもの** である (§1 を参照)。認証済みのクライアント 1 台でサーバーを停止させられる状態を避けることが目的。

### 6.1 値

| 対象 | 上限 | 超過時 |
|---|---|---|
| HTTP リクエストのボディ | **1 MiB** | 413 |
| 1 リクエストの `reports` の件数 | **64** | 400 `limit_exceeded` |
| 1 リクエストの `actions` の件数 | **64** | 400 `limit_exceeded` |
| 1 イベントの `data` のサイズ | **8 KiB** | 400 `limit_exceeded` |
| `room_info` のサイズ | **64 KiB** | 400 `limit_exceeded` |
| ユーザー名 | **32 文字** | 400 `bad_request` |
| 部屋の人数 | **2〜4** | 400 `bad_request` |
| 保持するレコード数 | **100** (10 秒分) | 410 `sync_too_old` |
| 部屋数 | 環境変数 `ROOM_LIMIT` | 503 `room_limit_reached` |
| 部屋番号の採番の試行回数 | **32 回** | 503 `room_limit_reached` |

### 6.2 根拠

イベント件数の 64 は、移動の報告を毎フレーム送る想定 (60 fps で 100 ms なら 6 件) に対して十分な余裕がある。クライアントは送信前に同一の `(from, type)` の報告を合流させるため (§2.2)、正常なクライアントが 64 件に達することはない。この上限は、壊れたクライアントや悪意ある送信に対する防波堤として置く。
