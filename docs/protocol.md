# ShoutWars 通信仕様

ShoutWars のクライアントとサーバーの間の通信仕様を定める。

本仕様が定めるのは **クライアントとサーバーの間で見える振る舞い** に限る。送受信する値、エラー、順序と保証がそれにあたる。ここが食い違う場合は実装を直す。クライアントは別のリポジトリにあり、実装が独自に動くと相手は何を頼りに書けばよいか分からなくなる。

**内部の作りは本仕様の対象ではない。** データ構造、掃除の時機、順位を決めるハッシュ関数といったものは実装が決めてよい。本仕様が具体を挙げていても、そのとおりに作ることを求めてはいない。時間や件数の値も、規則ではなく既定である。

対象 API バージョンは **`/v3`**。[`/v2` からの変更点](#v2-からの変更点) を別に示す。


## 概要

### 責務

サーバーの責務は次の 3 つに限られる。

1. **部屋の管理** — 作成、参加、寿命、メンバーシップ
2. **同期** — 全ユーザーのイベントを集約し、全員に同一の集合を同一順序で配る
3. **可用性の防衛** — サイズ・件数の上限、期限切れの回収

### 非責務

サーバーが明示的に行わないこと。

#### ゲームの状態を持たない・解釈しない

サーバーはゲームロジックを一切実行しない。ゲームの状態はすべてクライアントが持つ。

#### チート対策を行わない

ゲームの仕様上、クライアント側でのチートは容易である (音声認識をキー入力に差し替えるだけで有利になる)。したがってサーバー側で部分的に対策しても意味がないため、行わない。

> **可用性はこれとは別である。** 「チート対策をしない」は「何も検証しない」を意味しない。サイズ・件数の [上限](#制限値) はチート対策ではなく、メモリ枯渇によるサービス停止への対策であり、責務に含まれる。

#### 特定の型の中身を解釈しない

次の値はサーバーにとって不透明であり、汎用の値型のまま保持して素通しする。

| 値 | 位置 |
|---|---|
| `room_info` の中身 | 部屋ごとに 1 つ |
| 各イベントの `data` の中身 | イベントごと |

サーバーはこれらを読まず、書き換えず、検証しない (サイズの上限を除く)。

### 用語

| 用語 | 定義 |
|---|---|
| **部屋 (room)** | 同期の単位。ロビーとゲームの 2 状態を持つ |
| **ユーザー (user)** | 部屋への 1 回の参加。UUIDv7。同一人物との対応は保証しない |
| **セッション (session)** | 認証の単位。部屋の作成・参加時に発行される |
| **tick** | 同期の単位時間。既定 100 ms。幅はサーバーが決める |
| **同期レコード (sync record)** | 1 tick 分のイベント集合 |
| **tick 番号** | 部屋の作成時を 0 とする連番。レコードの識別子であり順序 |
| **報告イベント (report)** | 状態の複製。送信者には返らない |
| **確認イベント (action)** | コマンドの確定。送信者にも返る |
| **部屋主 (owner)** | 部屋にいるユーザーのうち、ID が最も若い者 |

## 同期モデル

### 同期の概観

ゲーム中の通信は **tick** という単位で進む。1 tick は既定で **100 ms** であり、実際の幅はサーバーが決めて `tick_ms` として通知する ([tick の進行](#tick-の進行))。

サーバーは各 tick について **同期レコード** を 1 つ持ち、全ユーザーのイベントを集約して、全員に同一の集合を同一順序で配る。サーバーはイベントの中身を解釈しない。

レコードには **部屋の作成時を 0 とする連番 (tick 番号)** が付く。これがレコードの識別子であり、順序であり、経過時間の基準でもある。ゲーム内の残り時間などは、この値を数えて全員で一致させる。クライアントのローカル時計は使えない ([順序の規則](#順序の規則))。

イベントには 2 種類あり、**別の仕組み** である。

| | 報告イベント (`reports`) | 確認イベント (`actions`) |
|---|---|---|
| 正体 | **状態の複製** | **コマンドの確定** |
| 例 | 座標と速度 | アイテムの取得 |
| 送信者への返却 | されない | **される** |
| 送信者のローカル適用 | **即時** (待たない) | **確定を待つ** |
| 遅延したとき | **破棄** | **1 tick まで持ち越し** |
| 順序保証 | 不要 | **必須** |

### 報告イベント — 状態の複製

**用途:** 「今こうなっている」を伝えるもの。座標と速度が典型。

- 送信者は **自分の分を即座にローカル適用する。** 応答を待たない
- 受信側は速度を使って **外挿 (dead reckoning) する。** 速度が無いと他プレイヤーの動きが不連続になる
- 値は絶対値であり、上書きされれば直る。**個々の到達は保証しない**
- **遅れて届いた report は破棄する。** 古い座標を今さら適用すると巻き戻って見える

#### 合流はクライアントの責務

移動の報告は毎フレーム発生し得るため、1 tick (100 ms) の間に同じ内容の報告が何件も溜まる。値が絶対値である以上、**最後の 1 件以外は無意味** である。

**この間引き (合流) はクライアントが送信前に行う。** サーバーは受け取ったものをそのまま中継する。

サーバー側で合流させてはならない。「同じ `type` の報告は上書きされる」というゲームの意味をサーバーが理解することになり、[非責務](#非責務) に反する。

### 確認イベント — コマンドの確定

**用途:** 複数人が同時に行うと衝突するもの。アイテムの取得が典型。

- 送信者は **ローカル適用しない。** サーバーが確定させた tick で、送信者を含む全員が同時に適用する
- そのため `actions` は **送信者にも返る**
- 衝突は **クライアント側で全員が同じ規則を適用して** 解決する。受信順に処理し、先に成立した方を採用する
- 遅れて届いた action は **次の tick に持ち越す。** 持ち越しは 1 tick まで

### 順序の規則

サーバーが定める順序は次のとおり。**クライアントは受信順に処理するだけ** であり、自分で並べ替えてはならない。

```
順序 = (tick, その tick での送信者の順位, 送信者内の送信順)

送信者の順位 = hash(tick ++ user_id) の昇順
```

| 保証 | 根拠 |
|---|---|
| 全員が同じ順序を受け取る | tick 番号はサーバー採番、ユーザー一覧は全員一致 |
| **同一送信者内の順序は崩れない** | 送信者ごとの配列をそのまま連結する |
| プレイヤー間に恒久的な偏りがない | 順位が tick ごとに入れ替わる |
| **時計に依存しない** | タイムスタンプを順序に使わない |

#### イベント ID は順序を決めない

**イベント ID は識別子であり、順序には使わない。**

イベント ID をクライアントが生成する UUIDv7 とし、その大小で衝突を裁定してはならない。時刻部の物差しがクライアントのローカル時計になるためである。ローカル時計は数百 ms 単位でずれ得るので、ずれが tick 幅を超えると **衝突は毎回同じプレイヤーに倒れ**、当事者は原因に気づけない。

同一 tick 内は定義上「同時」であり、時刻の前後を争うこと自体に意味がない。tick をまたぐ順序は tick 番号が担保する。

**順位の決め方はサーバー内部で完結する。** 「同一送信者内の順序が崩れない」ことさえ守れば、決め方を変えてもプロトコルとクライアントは変わらない。

### tick の進行

#### パイプライン化

クライアントは **`tick_ms` 周期でリクエストを送信する。前回の応答を待たない。**

```
周期 = max(tick_ms, ネットワーク往復)
```

- in-flight は常に 1 本まで。周期が来ても前回の応答が未着なら、到着まで待つ
- イベントの蓄積は継続し、送信時に送信キューをまとめて送る
- 応答は次の窓の途中で到着する。**受信した時点で適用する** (余分に寝かせない)

**応答を待ってから次の窓を開始してはならない。** 蓄積窓とネットワーク往復が直列に並び、周期にラグが丸ごと加算される。

tick `N` のレコードが集める窓は `[作成 + N × tick_ms, 作成 + (N+1) × tick_ms)` である。

**tick 幅はサーバーが決め、参加時の応答で `tick_ms` として通知する。** クライアントはこの値に従い、自分で埋め込んではならない。クライアントのバージョンは完全一致を要求する ([クライアントのバージョン](#クライアントのバージョン)) ため、値を変えるたびに再配布が必要になることを避ける。

#### 締め切り

**レコードは窓の終わりで締め切る。** 窓は絶対時刻で決まるため、レコード `N` は窓 `N` に届いたイベントそのものであり、tick 番号と経過時間はずれない。

**全員が早く到着しても、待たずに締め切ってはならない。** 早く締め切ると次の窓が `tick_ms` より長くなり、`tick_ms` 周期で送る正常なクライアントが同じ窓へ二度書き込む。`403 already_synced` を受け取ることになる。締め切りを早めて縮められるのは応答までの待ち時間だけで、進む速さは変わらない。

**締め切りと同時に次のレコードを開く。** 「締め切り済みだが次が開いていない」隙間が生じてはならない。隙間があると、3 人以上の部屋で正常なクライアントが書き込み先を失う。

### 配送 — カーソルはクライアントが持つ

**クライアントがリクエストに `next_tick` を含める。** サーバーはその番号以降のレコードを返す。

**カーソルはどの応答でも `next_tick` という同じ名前で返る。** クライアントは受け取った値をそのまま次のリクエストに入れる。加算も減算も要らない。

**サーバーが「渡した」と推定してはならない。** レスポンスを書き出す前にカーソルを進めると、レスポンスが届かなかった場合にそのレコードが永久に失われ、しかも検出されない。クライアント側の HTTP タイムアウトで容易に発生する。

| 性質 | |
|---|---|
| **冪等** | 同じ `next_tick` で何度投げても同じものが返る |
| **自己修復** | 取り損ねても次の同期で自動的に再送される |
| **推定が無い** | サーバーは「届いたはず」と仮定しない |

`next_tick` を進めるのはクライアントが **受信して適用し終えたとき** である。応答が返した値をそのまま使えばよい。

#### 保持期間

サーバーはレコードを **10 秒 (100 tick) 分** 保持する。それより古い `next_tick` を申告された場合は追いつけないため、専用のエラーを返し、クライアントは再参加して `room_info` から状態を作り直す ([遅延・不在・脱落・復帰](#遅延不在脱落復帰))。

### 遅延・不在・脱落・復帰

**不在**と**脱落**を分ける。

| | 判定 | 扱い |
|---|---|---|
| **不在** | レコードの締め切りに間に合わなかった | そのレコードで不在として報告する |
| **脱落** | レコードの保持期間 (100 tick = 10 秒) にわたって応答がない | 部屋から除去する |

#### 復帰

復帰に専用の手順は無い。**同じセッションで、保持していた `next_tick` を申告して `/room/sync` を再開するだけ** でよい。取りこぼしたレコードがまとめて返る。

保持期間を超えて不通だった場合は脱落しているため、再参加が必要になる。両者を同じ長さにしてあるので、「部屋には残っているのに追いつけない」状態は生じない。

#### 不在中のクライアントの契約

- `actions` 由来の状態を **自力で進めてはならない。** 復帰後、未受信のレコードを順に適用する
- `reports` 由来の外挿は続けてよい

### メンバーシップ

**ユーザー一覧は、レコードの締め切り時点で固定したスナップショットとして `sync` の応答で返す** (`room_users`)。返すのは、今回返した最後のレコードの締め切り時点のものである。

- 一覧は **ユーザー ID の昇順** に並ぶ。ユーザー ID は UUIDv7 で参加順に増えるため、先頭が常に部屋主になる ([部屋主](#部屋主))
- 各ユーザーは [不在](#遅延不在脱落復帰) かどうかを持つ
- ゲームが開始しているかどうかも同じ応答で伝える

**応答の生成時点の一覧を返してはならない。** 同一レコードに対する各人の応答は異なる時刻に生成されるため、その時点の一覧を返すと人によって内容が食い違い、desync する。レコードに固定すれば、同じレコードを受け取った全員が必ず同じ一覧を受け取る。

**差分はクライアントが取る。** 「誰が抜けたか」を知りたい場合は前回の一覧と比べる。一覧は絶対値であり、取りこぼしても次の応答で上書きされて直る。差分の列から状態を組み立てる方式では、一度でも適用を誤ると黙って食い違ったまま進む ([報告イベント](#報告イベント--状態の複製) と同じ理由である)。

**サーバーはイベントを生成しない。** `reports` と `actions` に流れるものはすべてクライアント由来であり、サーバー発のものが混ざることはない。

### `room_info`

**遅延参加者用の初期状態スナップショットであり、権威ではない。**

- **参加時の応答でのみ返す。毎 tick 返さない。** 上限 64 KiB ([制限値](#制限値)) の値を毎 tick 全員へ配る負荷に見合わない
- 更新は **部屋主が `sync` のリクエストに含めて送る。** 他者から送られたものは無視される
- サーバーは **レコードの締め切り時点でスナップショットを差し替える** ([メンバーシップ](#メンバーシップ) と同じ規則)
- 他のクライアントへは、部屋主が通常のイベントで知らせる。各クライアントは自分の `room_info` を更新する

**到着時点で差し替えてはならない。** スナップショットと通知イベントが別々の境界で切り替わることになり、参加のタイミング次第で通知イベントを二重に適用する場合が生じる。締め切りに合わせれば境界が 1 本に揃う。

### desync 検出

**desync** とは、同じイベント列を受け取っているはずのプレイヤー間で状態が食い違うこと。アイテムを取れた人と取れていない人が同時に存在する、といった形で現れる。

**エラーも例外も出ない。** ゲームは何事もなく進行し続け、プレイヤーには「判定がおかしい」としか見えず、サーバーのログにも何も残らない。したがって、検出する仕組みを持たなければ原因の特定は事実上不可能になる。

[配送](#配送--カーソルはクライアントが持つ) のカーソルは取りこぼしを **予防** するが、クライアント側の適用ミス、`room_info` からの復元漏れ、報告イベントの合流の食い違いは防げない。**予防と検出は別の仕組みであり、両方を備える。**

#### 適用イベント数の照合

クライアントは、これまでに **受け取って処理したイベントの累計** を `applied` として送る。サーバーは自分が配った数を知っているため、比較するだけでよい。

**破棄したものも数える。** 遅れて届いた報告イベントは適用せず捨てるが ([報告イベント](#報告イベント--状態の複製))、それも 1 件として数える。数えるのは「サーバーが配った件数」と突き合わせるためであり、クライアントがその中身をどう扱ったかとは関係がない。ここを取り違えると、正常なクライアントが desync と判定される。

これで取りこぼしと二重適用を検出できる。

#### 検出時の扱い

サーバーは不一致を検出したら、レスポンスの `desync` を `true` にして全員に通知する。クライアントは通信エラーとして扱い、ゲームを終了してよい。**食い違ったまま続行するより望ましい。**

### サーバーが保証すること

1. 全ユーザーが **同一のイベント集合** を **同一順序** で受け取る
2. 同一のレコードを受け取った全員が、**同一のユーザー一覧** を受け取る
3. 同一送信者のイベントの相対順序は保存される
4. `sync` は **必ず 1 件以上のレコードを返す**
5. tick の境界と、イベントがどの tick に属するかは、**サーバーだけが決める**
6. 締め切られたレコードは **二度と変わらない**

### サーバーが保証しないこと

- ゲーム状態の正しさ (解釈しないため)
- チートの防止 ([非責務](#非責務) を参照)
- 個々の `report` の到達
- 同一人物が複数ユーザーとして参加しないこと (匿名参加のため識別手段がない)

## 部屋のライフサイクル

### 部屋の状態

部屋は **ロビー** と **ゲーム** の 2 状態を持つ。作成時はロビーであり、部屋主が開始するとゲームへ移る。**戻ることはない。**

| 状態 | 期限 | 参加 |
|---|---|---|
| ロビー | 作成から **10 分** | 可 |
| ゲーム | 開始から **20 分** | 不可 |

期限切れの部屋は削除される。**期限切れの部屋には参加できない。** 削除処理が周期実行である場合も、参加時に期限を確認すること。

### 参加コード

部屋 ID (UUID) は口頭で伝えられないため、別に短い **参加コード** を持つ。参加はこのコードで行う。コードは **6 桁の数字** とする。

- **参加コードは乱数で採番する。** 使用中のコードが出た場合は引き直す
- 引き直しの回数には上限を設け、超えた場合は `503 room_limit_reached` を返す。上限が無いと、コードが埋まってきたときに際限なく回る
- **削除されたコードの再利用に猶予は設けない**

### ユーザー

- ユーザーは **部屋への 1 回の参加** を表す。同一人物との対応は保証しない
- ユーザー ID は部屋の中で一意である
- ユーザー名は 32 文字以内
- **同一人物の重複参加は防がない。** 匿名参加であり識別手段がないため
- 人数の上限は部屋の作成時に 2〜4 で指定する

### 部屋主

- 部屋主は、部屋にいるユーザーのうち **ID が最も若い者**。ユーザー ID は参加順に増えるため、残っている中で最も早く参加した者にあたる
- 部屋を作成した者が最初の部屋主となる
- **部屋主が抜けた場合、次に早く参加した者が引き継ぐ。** 一覧は ID 昇順なので、次の者が先頭になるだけである ([メンバーシップ](#メンバーシップ))

部屋主だけができること。

- ゲームの開始
- `room_info` の更新

### クライアントのバージョン

`create` と `join` は `version` を受け取り、**完全一致のみを許可する。** 一致しない場合は `409 version_mismatch` を返す。

バージョンが異なるクライアントは、イベントの解釈やゲームロジックが食い違い、[desync](#desync-検出) を起こす。サーバーはイベントの中身を解釈しないため、どの差異が安全かを判断できない。したがって互換の範囲を設けず、完全一致を要求する。

クライアントはゲームを更新するたびに `version` を変更する。

### セッション

- 部屋の作成・参加時に発行する
- **暗号論的乱数で生成する。** UUIDv7 を使ってはならない
- [脱落](#遅延不在脱落復帰) で無効になる
- **部屋が期限切れで削除されたときも無効になる。** この場合のエラーは `401 invalid_session` である
- セッションが無効になったクライアントは、同期を停止しなければならない

セッション ID は bearer トークンであり、これを持つ者はそのユーザーとして振る舞える。UUIDv7 は先頭 48 bit がタイムスタンプで秘密にならず、残る 74 bit も RFC 9562 では実装依存とされていて **乱数とは限らない**。

### ゲームの開始

部屋主が開始すると、**新たな参加ができなくなる。** それ以外の意味を持たない。ゲームの進行そのものはクライアントが管理する。

開始した事実は `sync` の応答の `started` で全員に伝わる ([メンバーシップ](#メンバーシップ))。部屋主だけが知る状態にしてはならない。

### ゲームの終了

**サーバーは「ゲームが終わった」という概念を持たない。** 決着はクライアントが判定し、部屋は期限切れとともに削除される。

**同じ部屋での再戦は行わない。** もう一度対戦する場合は部屋を作り直す。

## API

エンドポイントは `/v3`。Request と Response の body は MessagePack で表す。Content-Type は `application/msgpack`。

環境変数 `PASSWORD` が設定されている場合、リクエストヘッダの `Authorization` に `Bearer ${PASSWORD}` を指定する。

`uuid` は UUID の文字列表現とする。**プリミティブでない型 (`RoomInfo`、`Event` の `data`) はサーバーが解釈しない** ([非責務](#非責務))。

以降のスキーマは構造を示す記法であり、そのままの文字列が流れるわけではない。値の位置に書かれた `string` や `uuid` は型を表す。

### `/v2` からの変更点

| 変更 | 理由 |
|---|---|
| **`sync_id` (UUID) を廃止し `tick` (整数) に置換** | 順序と経過時間の基準を兼ねる ([同期の概観](#同期の概観)) |
| `sync` のリクエストに **`next_tick`** を追加 | 配送のカーソルをクライアントが持つ ([配送](#配送--カーソルはクライアントが持つ)) |
| `sync` のリクエストに **`applied`** を追加 | [desync 検出](#desync-検出) |
| `sync` のレスポンスの **`room_users` をレコード単位に固定** | 応答の生成時刻で内容が変わらないようにする ([メンバーシップ](#メンバーシップ)) |
| イベント ID を **順序に使わない** | ローカル時計への依存を排除 ([順序の規則](#順序の規則)) |
| **`429` の規則を廃止** | パイプライン化 ([tick の進行](#tick-の進行)) |
| エラー body に **`code` を追加** | [エラー](#エラー) |
| `join` で **期限を確認** | [部屋の状態](#部屋の状態) |
| `create` / `join` の応答に **`tick_ms`** を追加 | tick 幅をサーバー側のつまみにする ([tick の進行](#tick-の進行)) |
| イベントの `event` を **`data` に改名** | 中身を解釈しない値であることを名前に合わせる |
| 部屋番号を **参加コード (`code`) に改称** | `user` の `name` と同じ本文に並び、紛らわしかった。形式を名前に含めない |

### `POST /v3/room/create`

部屋を作成する。

#### Request

```jsonc
{
  "version": string,   // クライアントのバージョン
  "user": { "name": string },  // ユーザー名 (32 文字以内)
  "size": number       // 部屋の人数 (2〜4 の整数)
}
```

#### Response

```jsonc
{
  "session_id": uuid,  // セッション ID
  "user_id": uuid,     // 自分のユーザー ID
  "id": uuid,          // 部屋 ID
  "code": string,      // 参加コード (6 桁の数字)
  "next_tick": number, // 最初の同期で申告するカーソル。作成直後なので 0
  "tick_ms": number    // tick の幅 (ミリ秒)
}
```

### `POST /v3/room/join`

部屋に参加する。ロビー状態の部屋にのみ参加できる。

#### Request

```jsonc
{
  "version": string,
  "code": string,      // 参加コード (6 桁の数字)
  "user": { "name": string }
}
```

#### Response

```jsonc
{
  "session_id": uuid,
  "user_id": uuid,
  "id": uuid,
  "room_info": RoomInfo, // 現在の部屋情報 (これで初期化する)
  "next_tick": number,   // 最初の同期で申告するカーソル
  "tick_ms": number      // tick の幅 (ミリ秒)
}
```

### `POST /v3/room/sync`

同期する。クライアントは `tick_ms` 周期で送信し、前回の応答を待たない ([tick の進行](#tick-の進行))。in-flight は 1 本まで。

#### Request

```jsonc
{
  "session_id": uuid,
  "next_tick": number,   // 次に受け取りたいレコードの tick 番号
  "applied": number,     // 受け取って処理したイベントの累計
  "reports": [{ "id": uuid, "type": string, "data": Data }],
  "actions": [{ "id": uuid, "type": string, "data": Data }],
  "room_info": RoomInfo  // 省略可。部屋主のみ有効
}
```

#### Response

```jsonc
{
  "next_tick": number, // 次のリクエストにそのまま入れる (今回返した最後のレコードの次)
  "room_users": [{  // ID 昇順。先頭が部屋主
    "id": uuid,
    "name": string,
    "absent": bool  // このレコードの締め切りに間に合わなかった
  }],
  "started": bool,  // ゲームが開始しているか
  "reports": [{
    "id": uuid,
    "tick": number, // このイベントが属するレコード (最後のレコード以外に属する場合のみ)
    "from": uuid,
    "type": string,
    "data": Data
  }],
  "actions": [ /* 同上。送信者自身のものも含む */ ],
  "desync": bool    // 不一致を検出した場合に true
}
```

- `reports` と `actions` は **サーバーが定めた順序** で並ぶ ([順序の規則](#順序の規則))。クライアントは並べ替えず、先頭から順に処理する
- 複数レコード分がまとめて返ることがある
- **必ず 1 件以上のレコードを含む**
- `room_users` と `started` は、今回返した **最後のレコードの締め切り時点** の値である ([メンバーシップ](#メンバーシップ))

### `POST /v3/room/start`

ゲームを開始する。部屋主のみが送信できる。新たな参加ができなくなる ([ゲームの開始](#ゲームの開始))。

#### Request

```jsonc
{ "session_id": uuid }
```

#### Response

```jsonc
{}
```

開始した事実は、全員の `sync` の応答の `started` に現れる。

### `GET /v3/status`

#### Response

```jsonc
{
  "room_count": number,
  "room_limit": number
}
```

## エラー

### エラーの形式

エラーは対応する 4xx / 5xx のステータスコードと、次の body で返す。

```jsonc
{
  "error": {
    "code": string,   // 機械可読な識別子
    "message": string // 人間向けの説明。UI に表示してよい
  }
}
```

`code` で分岐し、`message` は表示にのみ使う。これにより表示文言を変更してもクライアントの分岐が壊れない。

### エラーコード一覧

| ステータス | `code` | 意味 |
|---|---|---|
| 400 | `bad_request` | リクエストの形式が不正 |
| 400 | `limit_exceeded` | 上限を超えた ([制限値](#制限値)) |
| 401 | `unauthorized` | パスワードが不正 |
| 401 | `invalid_session` | セッションが無効または期限切れ |
| 403 | `not_owner` | 部屋主のみが可能な操作 |
| 403 | `already_synced` | 同一の窓に二度同期しようとした |
| 404 | `room_not_found` | 部屋が存在しない、または期限切れ |
| 409 | `version_mismatch` | クライアントのバージョンが合わない |
| 409 | `room_full` | 部屋が満員 |
| 409 | `game_started` | 既にゲームが開始している |
| 410 | `sync_too_old` | 申告された `next_tick` が保持期間外 |
| 413 | `limit_exceeded` | リクエストの本文が上限を超えた ([制限値](#制限値)) |
| 500 | `internal` | サーバー内部の誤り |
| 503 | `room_limit_reached` | サーバーの部屋数が上限に達している |

### 存在の秘匿について

**セッションの検証を先に行う。** セッションが無効なら `401 invalid_session` を返し、部屋の存在には言及しない。セッションが有効な場合にのみ、部屋の状態に応じた `404` や `409` を返す。

そのため `404 room_not_found` は **参加コードで参加しようとしたとき** に返る。既にセッションを持っているクライアントの部屋が期限切れになった場合は、セッションも同時に無効になるため `401 invalid_session` が返る ([セッション](#セッション))。どちらもクライアントの対応は同じである ([復帰の指針](#復帰の指針))。

### 復帰の指針

| `code` | クライアントの対応 |
|---|---|
| `sync_too_old` | 同期を停止し、再参加して `room_info` から作り直す |
| `invalid_session` | 同期を停止する。脱落している |
| `room_not_found` | 同期を停止する。部屋は消えている |
| `limit_exceeded` | 送信量を減らす。正常なクライアントは到達しない |
| `internal` | 再試行してよい。継続するようならサーバーの不具合 |

## 制限値

これらは **チート対策ではなく、メモリ枯渇によるサービス停止を防ぐためのもの** である ([非責務](#非責務) を参照)。認証済みのクライアント 1 台でサーバーを停止させられる状態を避けることが目的。

### 上限の一覧

| 対象 | 上限 | 超過時 |
|---|---|---|
| HTTP リクエストのボディ | **1 MiB** | 413 |
| 1 リクエストの `reports` の件数 | **64** | 400 `limit_exceeded` |
| 1 リクエストの `actions` の件数 | **64** | 400 `limit_exceeded` |
| 1 イベントの `data` のサイズ | **8 KiB** | 400 `limit_exceeded` |
| `room_info` のサイズ | **64 KiB** | 400 `limit_exceeded` |
| ユーザー名 | **32 文字** | 400 `bad_request` |
| 部屋の人数 | **2〜4** | 400 `bad_request` |
| 保持するレコード数 | **100** (10 秒分) | 410 `sync_too_old` |
| 部屋数 | 環境変数 `ROOM_LIMIT` | 503 `room_limit_reached` |
| 参加コードの採番の試行回数 | **32 回** | 503 `room_limit_reached` |

### 上限の根拠

イベント件数の 64 は、移動の報告を毎フレーム送る想定 (60 fps で 100 ms なら 6 件) に対して十分な余裕がある。クライアントは送信前に同一の `(from, type)` の報告を合流させるため ([報告イベント](#報告イベント--状態の複製))、正常なクライアントが 64 件に達することはない。この上限は、壊れたクライアントや悪意ある送信に対する防波堤として置く。
