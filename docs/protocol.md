# ShoutWars 通信仕様

本書は、ShoutWars におけるクライアント・サーバー間の通信仕様を定める。

本仕様が規定するのは、送受信されるデータ、エラー、イベント順序、および各種保証といった **クライアント・サーバー間の外部的な振る舞い** に限られる。クライアントとサーバーは別リポジトリで管理されているため、仕様と実装に乖離がある場合は実装側を修正する。

**内部実装は本仕様の対象外とする。** データ構造、クリーンアップのタイミング、順位決定用のハッシュ関数などは実装側の裁量で決定してよい。本仕様に具体例が記載されている場合でも、それと同一の実装を強制するものではない。

**規定される数値には規範的な値と既定値がある。** 内訳は [制限値](#制限値) に示す。実装間で一致させるべき値と、サーバー側で決定可能な値が存在する。

対象とする API バージョンは **`/v3`** である。[`/v2` からの変更点](#v2-からの変更点) は後述する。


## 概要

### 責務

サーバーの責務は以下の 3 つに限られる。

1. **部屋の管理** ― 作成、参加、有効期限、メンバーシップ
2. **同期** ― 全ユーザーのイベントを集約し、全員に同一のイベント集合を同一順序で配信する
3. **可用性の保護** ― サイズ・件数の上限管理、期限切れリソースの回収

### 非責務

サーバーが明示的に対象外とする項目を以下に示す。

#### ゲームの状態を持たない・解釈しない

サーバーはゲームロジックを一切実行しない。ゲームの状態はすべてクライアント側で管理する。

#### チート対策を行わない

ゲームの仕様上、クライアント側での不正行為（音声認識のキー入力への差し替えなど）が容易であり、サーバー側で部分的な対策を行っても効果が薄いため、チート対策は実施しない。

> **可用性の保護はチート対策とは区別される。** 「チート対策を行わない」ことは「リクエストの検証を行わない」ことを意味しない。サイズ・件数の [上限](#制限値) 管理はチート対策ではなく、メモリ枯渇によるサービス停止を防ぐためのものであり、サーバーの責務に含まれる。

#### 特定の型の中身を解釈しない

以下の値はサーバーにとって不透明（opaque）であり、汎用の値型として保持し、透過的に中継する。

| 値 | 位置 |
|---|---|
| `room_info` の中身 | 部屋ごとに 1 つ |
| 各イベントの `data` の中身 | イベントごと |

サーバーはこれらの内容の読み取り、改変、検証を行わない（サイズ上限のチェックを除く）。

### 用語

| 用語 | 定義 |
|---|---|
| **部屋 (room)** | 同期の単位。ロビーとゲームの 2 状態を持つ |
| **ユーザー (user)** | 部屋への 1 回の参加。同一人物との対応は保証しない |
| **セッション (session)** | 認証の単位。部屋の作成・参加時に発行される |
| **tick** | 同期の単位時間。既定値は 100 ms。幅はサーバーが決定する |
| **同期レコード (sync record)** | 1 tick 分のイベント集合 |
| **tick 番号** | 部屋の作成時を 0 とする連番。レコードの識別子および順序を表す |
| **報告イベント (report)** | 状態の複製。送信者には返送されない |
| **確認イベント (action)** | コマンドの確定。送信者にも返送される |
| **部屋主 (owner)** | 部屋にいるユーザーのうち、最も早く参加した者 |

## 同期モデル

### 同期の概観

ゲーム中の通信は **tick** という単位で進行する。1 tick の長さは既定で **100 ms** であり、実際の幅はサーバー側が決定して `tick_ms` として通知する ([tick の進行](#tick-の進行))。

サーバーは各 tick について **同期レコード** を 1 つ保持し、全ユーザーのイベントを集約して、全員に同一のイベント集合を同一順序で配信する。サーバーはイベントの中身を解釈しない。

レコードには **部屋作成時を 0 とする連番 (tick 番号)** が付与される。これがレコードの識別子、順序、および経過時間の基準となる。ゲーム内の残り時間などは、この tick 番号をカウントして全クライアント間で一致させる。端末ごとの時計（ローカル時刻）は使用できない ([順序の規則](#順序の規則))。

ローカル時計を使用してはならないのは、**全員で一致させるべき状態** と **マシン間での時刻比較** である。端末間で時刻がずれるだけでなく、経過時間もクロックの進み方の差が累積するためである。一方、自端末内のみで完結する単発の経過時間計測（往復通信時間の計測など）には、クライアントの時計を使用してよい。

イベントには 2 種類あり、**それぞれ異なる仕組み** で動作する。

| | 報告イベント (`reports`) | 確認イベント (`actions`) |
|---|---|---|
| 役割 | **状態の複製** | **コマンドの確定** |
| 例 | 座標と速度 | アイテムの取得 |
| 送信者への返却 | されない | **される** |
| 送信者のローカル適用 | **即時** (待たない) | **確定を待つ** |
| 遅延時の扱い | **受信側が破棄する** | **送信側が次の窓へ回す** |
| 順序保証 | 不要 | **必須** |

### 報告イベント ― 状態の複製

**用途:** 「現在どういう状態か」を伝える通知。座標や速度の同期が典型例。

- 送信側は、サーバーの応答を待たずに **自身のイベントを即座にローカル適用する**
- 受信側は、速度情報を用いて **デッドレコニング（外挿予測）を行う**（速度情報がないと他プレイヤーの描画が不連続になるため）
- 通知される値は絶対値であり、後続イベントで上書きされれば補正されるため、**個々のイベントの到達は保証されない**
- **遅れて届いた report は破棄する。** 古い状態を遅れて適用すると、座標の巻き戻り（ロールバック表示）が発生するためである

#### 合流はクライアントの責務

移動報告は毎フレーム発生し得るため、1 tick の間に同一内容の報告が複数蓄積することがある。しかし通知される値が絶対値である以上、**最新の 1 件以外は不要** である。

**この間引き (合流) はクライアントが送信前に行う。** サーバーは受信したイベントをそのまま中継する。

サーバー側で合流処理を行ってはならない。「同一 `type` の報告は上書きされる」というゲームセマンティクスをサーバーが解釈することになり、[非責務](#非責務) に反するためである。

### 確認イベント ― コマンドの確定

**用途:** 複数人が同時に実行すると競合するもの。アイテムの取得などが典型例。

- 送信側は、送信時に **ローカル適用を行わない**。サーバーによって確定された tick のタイミングで、送信者を含む全員が同時に適用する
- そのため、`actions` は **送信者自身にも返送される**
- 競合は、**全クライアントが同一のルールを適用して** 解決する。受信順にイベントを処理し、先に成立した操作を採用する
- **action を破棄してはならない。** 送信が tick の収集ウィンドウ（窓）に間に合わなかった場合は、次のウィンドウで送信する。サーバーは受信したウィンドウのレコードにイベントを含め、全員が同一の順序で適用する。破棄したクライアントのみ状態が進まず [desync](#desync-検出) の原因となる

### 順序の規則

サーバーが決定するイベント順序は以下の通りである。**クライアントは受信した順序のまま処理を行い**、独自に並べ替えてはならない。

```
順序 = (tick, その tick での送信者の順位, 送信者内の送信順)

送信者の順位 = hash(tick ++ user_id) の昇順
```

| 保証 | 根拠 |
|---|---|
| 全員が同一の順序を受け取る | tick 番号はサーバーが一元採番し、ユーザー一覧は全クライアントで一致 |
| **同一送信者内の順序は維持される** | 送信者ごとの配列をそのまま連結する |
| プレイヤー間に恒久的な偏りが生じない | 送信者の順位が tick ごとに入れ替わる |
| **端末時刻に依存しない** | 順序決定にタイムスタンプを使用しない |

#### イベント ID は順序を決めない

**イベント ID は識別用であり、順序の決定には使用しない。** クライアント側で生成した、部屋内で一意な UUID であれば形式（バージョン）は問わない。

UUIDv7 のようにタイムスタンプを含む ID の大小比較によって競合を裁定してはならない。各端末のローカル時計が基準となってしまうためである。端末間の時刻には数百 ms 単位のずれが生じ得るため、そのずれが tick 幅を超えると、**競合判定が常に特定のプレイヤーに有利（または不利）に偏り**、当事者には原因の判別が困難になる。

同一 tick 内のイベントは定義上「同時」として扱われるため、端末時刻による前後関係を争うこと自体に意味はない。なお、tick 間の順序は tick 番号によって保証される。

**同一 tick 内における送信者の順位決定はサーバー内部で完結する。** 「同一送信者内の順序を維持する」ことさえ守れば、順位決定アルゴリズムを変更してもプロトコル仕様やクライアント実装に影響を与えない。

### tick の進行

#### 送信の周期と位相

tick `N` のレコードがイベントを収集する時間枠（窓）は `[部屋作成時刻 + N × tick_ms, 部屋作成時刻 + (N+1) × tick_ms)` である。

**tick 幅はサーバーが決定し、参加時の応答で `tick_ms` として通知する。** クライアントはこの値に従うものとし、独自に値を埋め込んではならない。クライアントのバージョンは完全一致を要求するため ([クライアントのバージョン](#クライアントのバージョン))、tick 幅の調整に伴うクライアントの再配布を避けるためである。

**送信は、前回の応答を受信した時点で行う。** 同時に存在できる in-flight リクエストは常に最大 1 本とする。

- 参加直後の初回送信は、事前の応答を待たずにただちに行う
- イベントの蓄積はリクエスト送信中も継続して行い、送信時にキューに溜まったイベントをまとめて送る
- 応答は **受信した時点で即座に適用する**（余分な待機時間を設けない）
- **応答がタイムアウトした場合は、同一の `next_tick` で再送する。** これは応答受信以外で送信を行う唯一の契機であり、この処理がないと応答を喪失したクライアントが二度と同期を行えなくなる。カーソル操作は冪等である ([配送](#配送--カーソルはクライアントが持つ))

**イベントの蓄積を止めて通信往復を待ってはならない。** 蓄積処理とネットワーク往復が直列化し、送信周期に通信遅延がそのまま加算されてしまうためである。

応答が返却（解放）される時刻は窓の境界に固定されている ([締め切り](#締め切り))。そこを起点として次回リクエストを送信するため、位相は以下の値で安定する。参加直後の初回送信は窓内の任意の位置に到達するが、2 回目以降は位相が揃う。

```
到着位置 = 往復時間 mod tick_ms
周期     = tick_ms × (1 + floor(往復時間 / tick_ms))
```

往復時間（RTT）が `tick_ms` を超える場合、イベントを預けられるのは数窓に 1 回となる。**すなわち、周期は `tick_ms` の整数倍に量子化される。**

**クライアント側の自走タイマーで送信を駆動してはならない。** 送信基準をクライアント側に置くと、時計の進み方の差やタイマーの丸め誤差が累積し、サーバーの窓に対する送信位相が徐々にずれて窓の境界を跨いでしまう。応答受信を基準とすれば、サーバーの窓境界から与え直されるため誤差が累積しない。

| 症状 | 意味 |
|---|---|
| 自分が `absent` になる | 該当する窓にリクエストが 1 本も届かなかった |

**1 つの窓に 2 本以上のリクエストが届いてもよい。** 預け入れられたイベントは届いた順に連結され、2 本目以降のリクエストも窓の締め切りまで保留される。

進行が遅れているクライアントには過去レコードの応答が即座に返るため、その時点で開いている窓に次の預け入れが入る。これを起点とした次の送信も同一の窓に届くことがある。これをサーバー側で拒否してしまうと、待って送り直す間に窓が締め切られ、また即座に応答が返って次の窓に預け入れる、という悪循環から脱出できなくなる。保留すれば応答が窓の境界で解放されるため、1 往復で正常な位相に揃う。

**ただし、同一セッションのリクエストが保留されている間に次を送った場合は `409 sync_in_flight` で拒絶する。** in-flight を 1 本に保つクライアントであればこのエラーは発生しない。この制限により、異常なクライアント 1 台が保留を際限なく抱え込み、サーバーの接続を占有することを防ぐ。

#### 締め切り

**レコードは窓の終わりで締め切る。** 窓は絶対時刻で決まるため、レコード `N` は窓 `N` に届いたイベントそのものであり、tick 番号と実経過時間との対応関係は維持される。

**全員のリクエストが早く到着した場合でも、予定時刻を待たずに締め切ってはならない。** 早く締め切ると後続の窓が `tick_ms` より長くなり、tick 番号と経過時間の対応が崩れてしまう。ゲーム内のタイマー等は tick 数をカウントして同期しているため、ゲーム進行に直接悪影響を与える。締め切りを早めて短縮されるのは応答までの待ち時間のみであり、ゲームの進行速度自体が変わるわけではない。

**応答は、要求されたレコードが締め切られるまで返さない。** 最新状態に追いついているクライアントからのリクエストでは、要求された `next_tick` 以降の締め切り済みレコードが存在しないため、対象の窓が締め切られるまでリクエストはサーバー側で保留される。これは、**`sync` が必ず 1 件以上のレコードを返す** という保証 ([サーバーが保証すること](#サーバーが保証すること)) を満たすためである。なお、要求された `next_tick` に対する確定済みレコードが既にある場合は、期限を待たず即座に応答を返す。

これにより、**応答の解放時刻は常に窓の境界に固定される。** クライアントはこの返却タイミングを送信位相の基準として利用する ([送信の周期と位相](#送信の周期と位相))。リクエストが一定時間保留されるため、クライアント側の HTTP タイムアウト値は `tick_ms` より十分に長く設定しなければならない。

**締め切りと同時に次のレコードを開く。** 「締め切り済みだが次が開いていない」空白期間が生じてはならない。隙間があると、3 人以上の部屋において正常なクライアントがイベントの書き込み先を失う原因となる。

### 配送 ― カーソルはクライアントが持つ

**クライアントがリクエストに `next_tick` を含めて送信する。** サーバーはその番号以降のレコードを返す。

**カーソルはどの応答でも `next_tick` という同一のフィールド名で返る。** クライアントは受け取った値をそのまま次のリクエストに指定すればよく、クライアント側での加減算は不要である。

**サーバー側で「配信に成功した」と推定してはならない。** レスポンス送信前にカーソルを先行して進めてしまうと、レスポンスが届かなかった場合にそのレコードが恒久的に失われ、検出もできなくなる。これはクライアント側の HTTP タイムアウトなどで容易に発生する。

| 性質 | 説明 |
|---|---|
| **冪等性** | 同一の `next_tick` で何度リクエストしても同一の内容が返る |
| **自己修復性** | 応答を取り損ねても、次回の同期で自動的に再送される |
| **非推定** | サーバー側で「届いたはずである」と仮定しない |

**同一の `id` を持つイベントを二度受け取った場合、後から届いたものは破棄する。** 応答を取り損ねたクライアントは、確定を確認できていないイベントを次のリクエストでもう一度送信する。重複を排除せずに受け入れると全員が二重に適用してしまい、かつ配信総数は一致するため [desync 検出](#desync-検出) でも検知できなくなる。

`next_tick` カーソルを進めるのは、クライアントが **レスポンスを受信してイベントを適用し終えた時点** である。応答に含まれる値をそのまま使用すればよい。

#### 保持期間

**レコードを保持する期間はサーバー側が決定する。** それより古い `next_tick` を申告された場合は過去レコードに追いつけないため、専用のエラー（`410 sync_too_old`）を返し、クライアントは再参加して `room_info` から状態を再構築する ([遅延・不在・脱落・復帰](#遅延不在脱落復帰))。

**この保持期間は、脱落と判定するまでの時間と必ず一致させる。** 短い方のみを変更すると、「部屋に所属したままであるにもかかわらず追いつけない」ユーザーが発生する。クライアント側はこの保持期間を事前に把握できないため、自力では復旧できなくなる。

**部屋ごとの保持量が上限に達した場合は、保持期間を満たしていなくても古いレコードから順に破棄する。** 1 リクエストあたりのサイズには上限があるものの、送信回数と保持期間の積には上限がなく、過剰な送信によってサーバーのメモリが圧迫されるリスクがあるためである。保持量の上限を部屋ごとに設定することで、過剰に送信した部屋の保持期間が短縮されるにとどまり、他の部屋へ影響が及ぶのを防ぐ。なお、正常なクライアントによる 1 リクエストは数 KB 程度であり、この上限に達することはない。

### 遅延・不在・脱落・復帰

一時的な通信遅延である **不在** と、接続途絶による **脱落** を明確に区別する。

| | 判定条件 | 扱い |
|---|---|---|
| **不在** | レコードの締め切りまでにリクエストが間に合わなかった | そのレコードにおいて不在 (`absent: true`) として全員へ通知する |
| **脱落** | レコードの保持期間を超えて応答がない | 部屋から除去（切断扱い）する |

#### 復帰

復帰に特別な手続きは不要である。**同一セッションのまま、ローカルに保持していた `next_tick` を指定して `/room/sync` を再開するだけでよい。** 未受信のレコードが一括して返却される。

保持期間を超えて通信が途絶えていた場合は脱落しているため、部屋への再参加が必要となる ([保持期間](#保持期間))。

#### 不在中のクライアントの契約

- `actions` 由来の状態を **ローカルで先行して進めてはならない**。復帰後、未受信のレコードを順に受信・適用して追いつかせる
- `reports` 由来の外挿予測（デッドレコニング）は継続してよい

### メンバーシップ

**ユーザー一覧 (`room_users`) は、レコード締め切り時点で固定したスナップショットとして `sync` の応答に含めて返却する。** 返却されるのは、今回のレスポンスに含まれる最新レコードの締め切り時点における一覧である。

- 一覧は **参加順** に並ぶ。先頭のユーザーが常に部屋主となる ([部屋主](#部屋主))
- 各ユーザー要素には、その時点での [不在](#遅延不在脱落復帰) フラグが含まれる
- ゲームが開始しているかどうかのフラグ (`started`) も同一の応答で伝達される

**レスポンス生成時点の一覧を返してはならない。** 同一レコードに対する各クライアントへの応答は異なる時刻に生成されるため、生成時点の一覧を返すとクライアント間で内容が食い違い、[desync](#desync-検出) の原因となる。レコードの締め切り時点に固定することで、同一レコードを受け取った全員が必ず同一の一覧を受け取ることを保証する。

**メンバーの増減差分はクライアント側で検出する。** 退室などを検知したい場合は、前回の一覧と最新の一覧を比較する。一覧情報は完全なスナップショットとして提供されるため、仮に一時的な取りこぼしがあっても次回の応答で上書きされ復旧する。差分イベント列から状態を組み立てる方式では、一度でも適用を誤ると不整合が蓄積したまま進行してしまうためである ([報告イベント](#報告イベント--状態の複製) と同様の原則)。

**サーバーはイベントを独自に生成しない。** `reports` および `actions` に流れるイベントはすべてクライアント由来であり、サーバー発のイベントが混入することはない。

### `room_info`

**途中参加者向けの初期状態スナップショットであり、サーバー側で権威（Authoritative）を持つデータではない。**

- **`join` の応答でのみ返却する（毎 tick の配信は行わない）。** 上限 64 KiB ([制限値](#制限値)) のデータを毎 tick 全員へ配信する負荷を避けるためである
- **部屋の作成者には返却されない。** 作成者は自身で初期状態を決定し、後続の `sync` リクエスト等で送信する
- 更新は **部屋主が `sync` のリクエストに含めて送信する。** 部屋主以外のユーザーから送られたものは無視される
- サーバーは **レコードの締め切り時点でスナップショットを差し替える** ([メンバーシップ](#メンバーシップ) と同様の規則)
- 参加中の他のクライアントへの更新通知は、部屋主が通常のイベントで伝達する。各クライアントはそれを受信して自身の `room_info` を更新する

**リクエスト到着時点で差し替えてはならない。** スナップショットの更新と通知イベントの確定が別々の境界で切り替わることになり、参加のタイミング次第で新規参加者が通知イベントを二重に適用してしまう競合が発生する。レコードの締め切りタイミングに合わせることで、状態遷移の境界が一貫して揃う。

### desync 検出

**desync（状態の不整合）** とは、同一のイベント列を受信しているはずのクライアント間でゲーム状態に乖離が生じる現象を指す（例: あるプレイヤーからはアイテムを取得できたように見え、別のプレイヤーからは取得できていないように見えるなど）。

**プログラム上のエラーや例外は発生しない。** ゲーム自体は何事もなく進行し続けるため、プレイヤーには「判定がおかしい」としか認識できず、サーバーのログにも記録が残らない。したがって、明示的な検出機構を持たなければ原因の特定やデバッグが極めて困難になる。

[配送](#配送--カーソルはクライアントが持つ) におけるカーソル管理はパケット欠落を **予防** するが、クライアント側での適用ミス、`room_info` からの復元漏れ、報告イベントの間引き（合流）処理の齟齬などは防げない。**通信欠落の「予防」と状態不整合の「検出」は別の仕組みであり、両方を備える。**

#### 適用イベント数の照合

クライアントは、これまでに **受信して処理したイベントの累計件数** を `applied` として送信する。サーバー側が配信したイベント総数と照合することで、件数の整合性を検証する。

**受信後に破棄したイベントも件数に含める。** 遅延して届いたために適用せず破棄した報告イベント ([報告イベント](#報告イベント--状態の複製)) であっても、受信した以上は 1 件としてカウントする。この値はあくまで「サーバーが配信した件数」と突き合わせるためのものであり、クライアント内部で実際に適用されたか破棄されたかとは無関係である。このカウント処理を誤ると、正常に動作しているクライアントが誤って desync と判定される。

この照合機構により、イベントの欠落や二重適用を検出できる。

#### 検出時の扱い

サーバーはいずれかのクライアントで件数の不一致を検出した場合、レスポンスの `desync` を `true` に設定して全員へ通知する。クライアントはこれを通信エラーとして扱い、ゲームを終了してよい。**状態が食い違ったまま続行するよりも、速やかに中断することが望ましい。**

### サーバーが保証すること

1. 全ユーザーが **同一のイベント集合** を **同一順序** で受け取ること
2. 同一のレコードを受け取った全員が、**同一のユーザー一覧** を受け取ること
3. 同一送信者内のイベントの相対順序が維持されること
4. `sync` のレスポンスが **必ず 1 件以上のレコードを含む** こと
5. tick の境界、およびイベントがどの tick に属するかは、**サーバーのみが決定する** こと
6. 締め切られたレコードは **改変されない（不変である）** こと

### サーバーが保証しないこと

- ゲーム状態の正当性 (サーバーはゲームロジックを解釈しないため)
- チートの防止 ([非責務](#非責務) を参照)
- 個々の `report` イベントの到達
- 同一人物による複数ユーザーとしての重複参加防止 (匿名参加のため識別手段がない)

## 部屋のライフサイクル

### 部屋の状態

部屋は **ロビー** と **ゲーム** の 2 つの状態を持つ。作成直後はロビー状態であり、部屋主が開始操作を行うとゲーム状態へ遷移する。**ロビー状態へ戻る遷移は存在しない。**

| 状態 | 期限 | 参加 |
|---|---|---|
| ロビー | 作成から **10 分** | 可 |
| ゲーム | 開始から **20 分** | 不可 |

**上記の期限はゲーム自体のプレイ制限時間ではなく、放置された部屋を回収するための安全枠（サーバー側のタイムアウト上限）である。** 画面上の残り時間表示などはクライアント側で管理するものであり、この期限値をゲームタイマーとして参照してはならない。ゲーム本来の制限時間は、この期限値より短く設定すること。

**サーバーはこの値を変更してはならない。** クライアントはゲーム進行を tick 数で計測しており、その間は部屋が存在し続ける前提で動作している。この期限値をクライアントへ通知する経路は存在しないため、配備ごとに値を変更すると、クライアント側で原因不明の `401` エラーが発生する原因となる。

期限切れとなった部屋は削除される。**期限切れの部屋には参加できない。** 削除処理がバックグラウンドの定期実行である場合も、参加リクエストの処理時に必ず期限を確認すること。

### 参加コード

部屋 ID (UUID) は口頭等での伝達に適さないため、参加用の短い識別子として **参加コード** を発行する。部屋への参加はこのコードを用いて行う。参加コードは **6 桁の数字からなる文字列** とする。**先頭が `0` になる場合があるため、数値型ではなく必ず文字列として扱うこと。**

- **参加コードは乱数で採番する。** 使用中のコードと重複した場合は再抽選を行う
- 空きコードを採番できなかった場合は `429 room_limit_reached` を返す。再試行回数の上限は実装の裁量であり、外部仕様としては規定しない
- **削除された部屋の参加コードの再利用にあたり、猶予期間（クーリング期間）は設けない**

### ユーザー

- ユーザーは **部屋への 1 回の参加** を表す単位であり、同一人物との 1 対 1 の対応は保証しない
- ユーザー ID は部屋の中で一意である
- ユーザー名は 32 文字以内とする
- **同一人物による重複参加の防止は行わない** (匿名参加モデルであり、同一人物を識別する手段を持たないため)
- 参加人数の上限は、部屋の作成時に 2～4 人の範囲で指定する

### 部屋主

- 部屋主（オーナー）は、部屋に所属するユーザーのうち **最も早く参加した者** とする
- 部屋を作成したユーザーが最初の部屋主となる
- **部屋主が退出（脱落）した場合、次に早く参加したユーザーが引き継ぐ。** ユーザー一覧は参加順に整列されているため、一覧の先頭に繰り上がった者が新たな部屋主となる ([メンバーシップ](#メンバーシップ))

部屋主のみが実行可能な操作:

- ゲームの開始
- `room_info` の更新

### クライアントのバージョン

`create` および `join` はリクエストパラメータとして `version` を受け取り、**完全一致のみを許可する。** バージョンが一致しない場合は `409 version_mismatch` を返す。

バージョンが異なるクライアント間では、イベントの解釈やゲームロジックに齟齬が生じ、[desync](#desync-検出) を引き起こす原因となる。サーバー側ではイベント内容を解釈しないため、どの差異が安全かを判断できない。したがって後方互換などの許容範囲を設けず、完全一致を要求する。

クライアントは、ゲーム仕様や通信ロジックを更新するたびに `version` を変更すること。

### セッション

- 部屋の作成時および参加時に発行する
- **暗号論的に安全な乱数で生成する。** UUIDv7 を使用してはならない
- [脱落](#遅延不在脱落復帰) に伴い無効化される
- **部屋が期限切れで削除された場合も無効化される。** この場合のエラーは `401 invalid_session` となる
- セッションが無効になったクライアントは、直ちに同期処理を停止しなければならない

セッション ID は Bearer トークンとして機能し、これを持つクライアントはそのユーザーとして認証される。UUIDv7 は先頭 48 bit がタイムスタンプであるため秘匿性がなく、残る 74 bit も RFC 9562 では実装依存と規定されており **乱数性が保証されない** ためである。

### ゲームの開始

部屋主が開始操作を行うと、**以降の新規参加が不可能になる。** サーバー側における開始処理の意味はこれのみであり、ゲームの進行管理そのものはクライアント側で行う。

ゲームが開始された事実は、`sync` 応答の `started` フィールドを通じて全員に伝わる ([メンバーシップ](#メンバーシップ))。部屋主のみが把握する状態にしてはならない。

### ゲームの終了

**サーバー側には「ゲームが終了した」という概念や状態は存在しない。** 勝敗や終了条件の判定はすべてクライアント側で完結し、サーバー上の部屋は有効期限の到来とともに自動的に削除される。

**同一の部屋での再戦はサポートしない。** 再度対戦する場合は、部屋を新規に作成し直す。

## API

ベースパスは `/v3` とする。Request および Response のボディは MessagePack 形式を使用し、Content-Type は `application/msgpack` を指定する。

サーバーに環境変数 `PASSWORD` が設定されている場合、すべてのリクエストヘッダの `Authorization` に `Bearer ${PASSWORD}` を指定する。

定義されていないパスやメソッドへのリクエストに対しても、共通のエラー形式 ([エラーの形式](#エラーの形式)) でレスポンスを返す。バージョンの合わないクライアントがルーティング不能となった際にも、エラー理由を適切に読み取れるようにするためである。

スキーマ表記における `uuid` は UUID の文字列表現とする。また、**複合データ型 (`RoomInfo` や各イベントの `data`) はサーバー側では解釈しない** ([非責務](#非責務))。

以降に示すスキーマはデータ構造を説明するための記法であり、リテラル文字列がそのまま送信されるわけではない。値の位置に記載された `string` や `uuid` は型を表す。

### `/v2` からの変更点

| 変更 | 理由 |
|---|---|
| **`sync_id` (UUID) を廃止し `tick` (整数) に置換** | 順序と経過時間の基準を兼ねるため ([同期の概観](#同期の概観)) |
| `sync` のリクエストに **`next_tick`** を追加 | 配送カーソルをクライアント側で管理するため ([配送](#配送--カーソルはクライアントが持つ)) |
| `sync` のリクエストに **`applied`** を追加 | [desync 検出](#desync-検出) のため |
| `sync` のレスポンスの **`room_users` をレコード単位に固定** | 応答の生成時刻によって内容が食い違わないようにするため ([メンバーシップ](#メンバーシップ)) |
| イベント ID を **順序決定に使用しない** | クライアント端末の時刻への依存を排除するため ([順序の規則](#順序の規則)) |
| **`429` の独自制限規則を廃止** | 送信の周期と位相を仕様として定めたため ([送信の周期と位相](#送信の周期と位相)) |
| エラー body に **`code` を追加** | [エラー](#エラー) |
| `join` 処理時に **有効期限を確認** | [部屋の状態](#部屋の状態) |
| ユーザー一覧を **参加順** と定め、ユーザー ID に順序の意味を持たせない | ID は識別用であり、順序には使わないため ([メンバーシップ](#メンバーシップ)) |
| `create` / `join` の応答に **`tick_ms`** を追加 | tick 幅をサーバー側の設定パラメータとして制御可能にするため ([tick の進行](#tick-の進行)) |
| `sync` の応答に **`held_ms`** を追加 | 保留待機時間を除いた純粋な通信往復時間（RTT）を計測可能にするため |
| イベントの `event` フィールドを **`data` に改名** | 中身を解釈しないペイロードであることを命名に反映するため |
| 部屋番号を **参加コード (`code`) に改称** | `user` の `name` と同じ階層に並び紛らわしく、データ形式（番号）を名前に含めないため |
| **ステータスコードの見直し** | 下表を参照 |

`/v2` から変更されたステータスコードは以下の通り。**旧コードで条件分岐を行っているクライアントは修正が必要となる。**

| 事象 | `/v2` | `/v3` | 変更理由 |
|---|---|---|---|
| 認証の失敗 | 404 | **401** `unauthorized` | 404 は存在秘匿を意図していたが、パスワードは全エンドポイント共通であり秘匿の効果が薄いため |
| バージョンの不一致 | 400 | **409** `version_mismatch` | リクエスト形式自体の誤りではなく、クライアントとサーバー間の状態競合であるため |
| 部屋が満員 | 403 | **409** `room_full` | 権限不足ではなく、リソースの状態競合であるため |
| ゲームが開始済み | 403 | **409** `game_started` | 同上 |
| 部屋数が上限 | 403 | **429** `room_limit_reached` | クライアント起因のエラーではなく、時間経過で解消するリソース枯渇であるため。なお 5xx 系はリバースプロキシ等で本文が差し替えられる懸念があるため、4xx 系を採用 |

### `POST /v3/room/create`

部屋を作成する。

#### Request

```jsonc
{
  "version": string,   // クライアントのバージョン
  "user": { "name": string },  // ユーザー名 (32 文字以内)
  "size": number       // 部屋の人数 (2～4 の整数)
}
```

#### Response

```jsonc
{
  "session_id": uuid,  // セッション ID
  "user_id": uuid,     // 自身のユーザー ID
  "id": uuid,          // 部屋 ID
  "code": string,      // 参加コード (6 桁の数字の文字列。先頭が 0 になりうる)
  "next_tick": number, // 初回の同期で申告するカーソル (作成直後のため 0)
  "tick_ms": number    // tick の幅 (ミリ秒)
}
```

### `POST /v3/room/join`

部屋に参加する。ロビー状態の部屋にのみ参加できる。

#### Request

```jsonc
{
  "version": string,
  "code": string,      // 参加コード (6 桁の数字の文字列。先頭が 0 になりうる)
  "user": { "name": string }
}
```

#### Response

```jsonc
{
  "session_id": uuid,
  "user_id": uuid,
  "id": uuid,
  "room_info": RoomInfo, // 現在の部屋情報 (これで初期化する)
  "next_tick": number,   // 初回の同期で申告するカーソル
  "tick_ms": number      // tick の幅 (ミリ秒)
}
```

### `POST /v3/room/sync`

同期を行う。送信の周期と位相は [送信の周期と位相](#送信の周期と位相) に従う。

#### Request

```jsonc
{
  "session_id": uuid,
  "next_tick": number,   // 次に受け取りたいレコードの tick 番号
  "applied": number,     // 受け取って処理したイベントの累計件数
  "reports": [{ "id": uuid, "type": string, "data": Data }],
  "actions": [{ "id": uuid, "type": string, "data": Data }],
  "room_info": RoomInfo  // 省略可。部屋主のみ有効
}
```

#### Response

```jsonc
{
  "next_tick": number, // 次回リクエストにそのまま指定する (今回返却された最新レコードの次)
  "room_users": [{  // 参加順。先頭が部屋主
    "id": uuid,
    "name": string,
    "absent": bool  // このレコードの締め切りに間に合わなかったか
  }],
  "started": bool,  // ゲームが開始しているか
  "reports": [{
    "id": uuid,
    "tick": number, // このイベントが属するレコード (最新レコード以外に属する場合のみ付与)
    "from": uuid,
    "type": string,
    "data": Data
  }],
  "actions": [ /* 同上。送信者自身のものも含む */ ],
  "desync": bool,   // 不一致を検出した場合に true
  "held_ms": number // リクエストを受け取ってから応答を返すまでにサーバー側で保留された時間 (ミリ秒)
}
```

- `reports` と `actions` は **サーバーが定めた順序** で整列して返却される ([順序の規則](#順序の規則))。クライアントは並べ替えを行わず、先頭から順に処理する
- 複数レコード分がまとめて返却される場合がある
- **レスポンスには必ず 1 件以上のレコードが含まれる**
- `room_users` と `started` は、今回返却された **最新レコードの締め切り時点** のスナップショットである ([メンバーシップ](#メンバーシップ))
- クライアント側で送信から受信までの時間を計測し、そこから `held_ms` を差し引くことで **通信の往復時間 (RTT)** を算出できる

### `POST /v3/room/start`

ゲームを開始する。部屋主のみが送信できる。実行後は新たな参加ができなくなる ([ゲームの開始](#ゲームの開始))。

#### Request

```jsonc
{ "session_id": uuid }
```

#### Response

```jsonc
{}
```

ゲームが開始された事実は、全クライアントにおける `sync` 応答の `started` に反映される。既に開始済みの部屋に対して再度送信した場合は `409 game_started` を返す。

### `GET /v3/status`

#### Response

```jsonc
{
  "room_count": number,
  "room_limit": number
}
```

## エラー

### エラーの形式

エラー発生時は、対応する HTTP ステータスコード (4xx / 5xx) とともに、以下の body を返却する。

```jsonc
{
  "error": {
    "code": string,   // 機械可読なエラー識別子
    "message": string // 人間向けの説明文。UI に表示してよい
  }
}
```

クライアント側は `code` に基づいて処理を分岐し、`message` は表示目的にのみ使用する。これにより、将来的に `message` の文言が変更されてもクライアント側の分岐ロジックが壊れない。

### エラーコード一覧

| ステータス | `code` | 意味 |
|---|---|---|
| 400 | `bad_request` | リクエストの形式またはパラメータが不正 |
| 400 | `limit_exceeded` | 個別フィールドの上限を超過した ([制限値](#制限値)) |
| 401 | `unauthorized` | パスワードが不正 |
| 401 | `invalid_session` | セッションが無効または有効期限切れ |
| 403 | `not_owner` | 部屋主のみが実行可能な操作 |
| 404 | `not_found` | 指定されたエンドポイントが存在しない |
| 404 | `room_not_found` | 部屋が存在しない、または有効期限切れ |
| 405 | `not_found` | 指定されたパスに対して許可されていないメソッド |
| 409 | `version_mismatch` | クライアントのバージョンが合わない |
| 409 | `room_full` | 部屋が満員 |
| 409 | `game_started` | 既にゲームが開始している |
| 409 | `sync_in_flight` | 保留中の同期応答を待たずに次の同期リクエストを送信した |
| 410 | `sync_too_old` | 申告された `next_tick` がサーバーの保持期間外 |
| 413 | `limit_exceeded` | リクエストの本文サイズが上限を超過した ([制限値](#制限値)) |
| 429 | `room_limit_reached` | サーバー全体の部屋数が上限に達している |
| 500 | `internal` | サーバー内部エラー |

### 存在の秘匿について

**セッションの検証を先行して行う。** セッションが無効であれば直ちに `401 invalid_session` を返し、部屋の存在有無には言及しない。セッションが有効である場合に限り、部屋の状態に応じた `404` や `409` を返す。

そのため、`404 room_not_found` は原則として **参加コードを指定して部屋へ参加しようとしたとき** に返却される。既にセッションを取得済みのクライアントにおいて部屋が期限切れとなった場合は、セッションも同時に無効化されるため `401 invalid_session` が返る ([セッション](#セッション))。どちらのエラーであっても、クライアント側の対応方針は同一である ([復帰の指針](#復帰の指針))。

### 復帰の指針

| `code` | クライアントの対応 |
|---|---|
| `sync_too_old` | 同期を停止し、部屋へ再参加して `room_info` から状態を再構築する |
| `invalid_session` | 同期を停止する (脱落扱い) |
| `room_not_found` | 同期を停止する (部屋は削除されている) |
| `limit_exceeded` | 送信量を減らす (正常なクライアントでは発生しない) |
| `sync_in_flight` | in-flight リクエストを 1 本に制限する (正常なクライアントでは発生しない) |
| `internal` | リクエストを再試行する。エラーが継続する場合はサーバーの不具合 |

## 制限値

以下の制限値は、**チート対策ではなく、メモリ枯渇等のリソース圧迫によるサービス停止を防ぐためのもの** である ([非責務](#非責務) を参照)。認証済みのクライアント 1 台によってサーバー全体が停止する事態を回避することを目的とする。

### 実装の間で一致させる値

| 対象 | 上限 | 超過時 |
|---|---|---|
| 1 リクエストの `reports` の件数 | **64** | 400 `limit_exceeded` |
| 1 リクエストの `actions` の件数 | **64** | 400 `limit_exceeded` |
| 1 イベントの `data` のサイズ | **8 KiB** | 400 `limit_exceeded` |
| `room_info` のサイズ | **64 KiB** | 400 `limit_exceeded` |
| ユーザー名 | **32 文字** | 400 `bad_request` |
| 部屋の人数 | **2～4** | 400 `bad_request` |
| 参加コード | **6 桁の数字の文字列** | 404 `room_not_found` |

これらの値は、クライアントが **動作する前に把握しておく必要がある定数** である。入力 UI の文字数制限、`room_info` に格納するデータ構造の設計、1 つの窓に収めるデータ量の見積もり等に使用される。実行時のネゴシエーションでは対応できないため、別実装間でも同一の値を用いなければならない。

### サーバーが決める値

| 対象 | 超過時 |
|---|---|
| HTTP リクエストのボディ | 413 `limit_exceeded` |
| レコードの保持期間 | 410 `sync_too_old` |
| 部屋ごとの保持量 | 410 `sync_too_old` |
| 部屋数 | 429 `room_limit_reached` |

**クライアントは上限を超過した際の振る舞いのみを把握していればよい。** 値そのものは配備先のマシンスペックや運用の都合によって決定されるため、共通仕様としては規定しない。

### 上限の根拠

イベント件数の上限値（64 件）は、移動報告を毎フレーム送信する想定 (60 fps、既定の tick 幅 100 ms の場合は 1 窓あたり 6 件) を基準に置いた値である。クライアントは送信前に同一 `(from, type)` の報告イベントを間引き（合流）するため ([報告イベント](#報告イベント--状態の複製))、1 窓あたりの実件数はゲームが同時に扱う報告種別の数によって概ね決まる。

この上限は、異常なクライアントや過剰送信に対する防波堤として設けている。**必要とされる件数はゲームの設計によって変動するため、マージンが不足する場合は本仕様の改訂としてこの値を引き上げる。** 実装間で一致させるべき値であるため、変更時は仕様を改定した上で双方の実装を揃えること。
